日期：2026-09-07。状态：本轮软件候选已实现并完成本地交付；尚未通过整机或商业放行。

用户已确认按产品化推进。新增批次为统一手机网页入口、首次配网与换网引导、逐台开箱状态、稳定绑定码及设备服务地址保护，具体契约见 [ADR 0007](../adr/0007-product-onboarding-and-same-origin-console.md)，实际结果见[产品化批次记录](../reports/2026-09-07-productization-onboarding.md)。本地网页与软件候选更新不等于正式域名发布、样机烧录或零售放行；真实验收仍按下面 G0–G7 执行。

## 4. 可替换架构的实际改造范围

### 模型与服务

- 复用 RealtimeAsrSession、RealtimeLlmProvider、RealtimeTtsSession，采用显式的小型注册表；模型目录必须真正控制调用的实现和模型。
- 经典路线的 ASR、LLM、TTS 各自绑定服务、端点、凭据引用、能力和参数；不要求三者来自同一家。当前保留 Qwen ASR、DeepSeek LLM、Qwen TTS 组合，原配置不被豆包覆盖。
- 每个智能体选择 `cascade` 或 `realtime_s2s`。豆包作为一个端到端会话后端，模型为 `1.2.6.1`、首个候选音色为 VV；不伪装成三个独立 Provider，也不重复记 ASR/LLM/TTS 费用。其失败不会静默换成经典路线，用户可手动切回。
- 模型与音色作为兼容组合原子保存。网页按路线能力显示参数：首版豆包不提交 LLM 温度或 TTS 语速，仍保留已实现白名单工具的开关；旧经典参数保留供切回使用。不同角色不能串用历史，切换路线但保留同一角色时维持已授权的短期上下文。
- 豆包候选默认禁用且不设为默认；部署开关、服务端凭据和目录启用均满足后才可用，生产还要求真机放行声明。管理员完成启用并设默认后，所有新建角色/首次认领入口统一采用目录默认；既有角色不批量改写。
- 在本轮开始前解析并冻结配置；修改角色、模型或参数从下一轮生效。代码插件随部署版本加载，避免播放中热卸载。
- 私有参数、供应商事件、音色约束和错误格式收进适配器。共享连接由应用回收，单轮资源由该轮取消；取消后旧事件不得再次下发。
- 当前设备协议保持 16kHz 单声道、60ms Opus 上行和 24kHz/60ms Opus 下行；TTS 在服务端统一成 24kHz 单声道 S16LE PCM 后复用现有编码与节奏控制。格式转换放在边界。
- 这些音频格式是当前协议版本的约定；未来新增格式通过能力校验和兼容版本支持，不能直接改全局常量让旧设备失效。
- 实际请求、日志身份和计费身份一致；主备尝试分别计量。S2S 按供应商会话/响应标识幂等记录，取消或失败也保留可能产生费用的尝试；只保存用量中的数字计数，不保存原始响应、音频或正文。未知成本使用 `null` 和明确状态，页面显示已知成本小计及未知记录数，不能解释为免费。

### 会话、硬件与通信

- 会话内核统一负责轮次开始、失效、取消、播放归属及结束；复用 PlaybackCoordinator、ConnectionLease 和现有背压机制。
- 沿用 Board、AudioCodec、Display、Protocol。引脚、声道选择、数据位移和校准参数集中在板型配置；新外设通过驱动适配。
- 分开表达物理能力、协议能力和产品策略；不让 CAM/NOCAM 宏代替这三类判断。
- Wi-Fi/以太网/蜂窝等 IP 接入使用适当的网络实现；BLE 配网和 BLE 全程传音频是两个不同需求。后者需要通信适配及手机/网关链路，届时单独开发。
- 不为尚未选择的 MCU、屏幕或通信链路制造空驱动。已明确的替换点必须有接口和替换验证。

### 协议与配置的唯一来源

- HTTP 边界沿用项目现有 OpenAPI 生成路径；设备事件沿用 contracts/device-ws-v1.json 并补行为/兼容性测试；Python 内部使用共享类型和 Protocol。
- 配置区分期望版本、已下发版本和设备已应用版本；发送成功不能显示为已经生效。
- 先确定接口变化及兼容策略，再并行开发两端。旧设备未知可选字段应按协议处理；破坏性变更显式升级版本。

替换验收：只换 LLM、只换 ASR、只换 TTS；经典路线的主备切换；同一角色经典 → 豆包 → 经典；不同角色历史隔离；不兼容音色被拒绝；同轮不混配置；工具取消/撤权与用量防重；两种板型共享会话测试；合法引脚变化不修改 Application 或云端业务。模拟服务通过与真实服务接通分别记录。接口决策见 [ADR 0006](../adr/0006-selectable-voice-routes.md)。

## 5. 真机语音和表情的调试顺序

1. 验证输入：同一板采集固定人声、安静和背景噪声样本，检查 I2S、声道、位移、采样率、增益、底噪和削顶；实际听取样本。有电平不等于录清楚。
2. 使用已有 BOOT 手动开听入口，隔离唤醒问题，贯通收音、识别、回复、合成、解码和扬声器；诊断模式调整另作独立变更。
3. 输入正确后测试唤醒：距离、角度、不同说话人、环境噪声与误唤醒；一次只改一个变量，不能用更换模型掩盖输入问题。
4. 用相同语料检查 VAD：长句中停顿、短句、数字、夹英文、说话尾音、续聊窗口边界；NOCAM 的 100ms 静音尾作为明确风险验证，再决定参数或算法。
5. 表情由真实设备状态驱动。若产品承诺音量口型，就完成共享 PCM 电平事件接入并验证；当前 NOCAM GIF 成功不等于口型已经实现。
6. 明确验证声音开始、声音结束、网络断流、按键停止后表情是否正确退出；无新音频帧时也不能一直张嘴。半双工首版不因此承诺自然语音插话。

固定矩阵覆盖短长句、数字、英文、时间、续聊、窗口外静默、停止和再唤醒。把旧 30 轮矩阵的场景纳入统一测试记录，能复用同一证据时不重复整套口测。

金样机沿用现有正式指标：经典与豆包分别执行两组各 50 次、每组至少 5 个会话；每组成功率至少 98%，软件首响 P50 不超过 2000ms、P90 不超过 2500ms。两条路线的样本、成功率和分位数分别计算，不能合并后宣布都通过。口径为服务端确认语音结束到对应 `speaker_pcm_started`，这是软件代理指标；两条路线必须记录同一事件口径，不把合成音频接通或收到云端首包当作设备首响。实际听见声音的时间另用同一外部录音测量，不混用时钟或冒充声学结果。

失败、超时、成功降级都保留；经典路线成功降级单独标记，不能删掉慢样本；豆包不可用时的提示与手动切换另验，不能计成豆包成功。静默负例单独成组，不充当成功语音请求。另做 2 小时连续对话与 8 小时待机，人工确认无沉默、截尾、断音、串轮、爆音、错脸、显示冻结或重启。豆包的云端、网关和真机步骤分别见[验收手册](../runbooks/doubao-acceptance.md)。

## 6. 商业化与生产必须补齐的闭环

- 开箱：Wi-Fi 密码错误、验证码过期、设备离线、重复认领、刷新页面、断网恢复，都有可理解的下一步。建议用 10 名首次接触产品的成年人验证，至少 9 人无需研发提示在 3 分钟内完成配网认领，然后各完成 10 轮交互。
- 服务权益：明确新设备赠送一次、账户共享与顺延、额度扣减、到期提示和续用方式。硬件销售渠道可独立于自建支付；若承诺在线付费续期，则支付回调幂等、退款、对账和权益一致性必须在售卖前完成。
- 用户数据：查看、修改、导出、关闭、删除记忆与账号注销有明确范围；旧存储及备份恢复不得悄悄复活已删除数据。默认不留原始音频和逐句正文；调试样本需单独授权并设清理期限。
- 解绑与售后：对话中解绑及时撤权；转售后新用户不继承旧记忆；换机不丢正确账户权益，也不重复赠送；恢复出厂与重新配网行为可解释。
- OTA：使用正式发布通道；校验固件完整性和设备适配；演练下载失败、断电、坏固件、联网失败及回退。固件签名、启动信任与设备密钥生命周期在生产安全评审中完成设计与验证，不在试验板上盲目烧写不可逆配置。
- 生产：维护 BOM、接线/硬件版本、板型配置、资产和固件哈希、工位版本、逐台身份与质检结果；当前首售所需结构、电源、温升、耐久及供应风险列入硬件评审。
- 工位：复用已有一次构建、多台刷写、身份绑定与失败恢复流程。逐台验证屏幕、麦克风、扬声器、按键、配网、认领和三轮对话；失败设备不能因为刷写校验通过就出厂。
- 容量：区分空闲连接、模拟语音负载和真供应商小样本。现有手册的 1000 空闲连接/50 路语音是待验证目标，不是已有能力；按 5→20→50 路测曲线并标明服务器规格、CPU、内存、转码进程和延迟。限售规模不能超过实测且留有余量的容量。
- 运维：按设备/轮次定位失败；区分 ASR、LLM、TTS、网关和设备播放；有告警接收人、问题分级、恢复手册、数据备份与恢复演练。恢复目标应由实测结果确定并记录。
- 成本：单台总成本计入物料、装配测试、包装物流、售后返修分摊；持续服务另计云资源、ASR 时长、LLM token、TTS、短信/邮件等实际使用。统计普通与高频用户，不凭少量聊天估计“无限使用”。
- 授权与权限：维护软件依赖、固件算法、表情资产和音色的来源与商业使用条件；研发、客服、工厂和普通用户分别验证访问权限，工厂不能读取用户记忆或发布 OTA。每个新市场及供应商重新核对适用范围。
- 市场适用要求：首售前根据最终硬件、电源/电池、无线方式和销售地区确认所需测试、文件、标签、隐私与售后要求及外协周期。本计划不表示这些审核已通过。

## 7. 每次开发的固定工作流

需求及完成标准 → 定位调用链与现有实现 → 复现缺陷或确认接口 → 小范围实现 → 自动检查 → 双进程/接口联调 → 相关真机检查 → 独立审查 → 本地逻辑提交 → 候选发布包 → 灰度与观察。

- 每个任务必须记录问题、受影响边界、验收命令或实测方法、数据变化与回退方式。
- 同一个核心文件只有一个整合负责人。Provider、固件和网页代理可并行工作，按共享契约汇合；代理并发不等同于同数量的人类工程师。
- 复用现有测试框架和 CI。正常单元、协议模拟、真实双进程、真实模型、真实设备、真实用户是不同层次；验收报告分别标记通过、失败、未测。
- 数据库迁移先在现有数据库副本验证；尽量兼容旧应用再删除旧字段。回退不能简单恢复旧数据库而覆盖用户的新数据。
- 旧固件与新后端、新固件与过渡后端的兼容范围写入发布清单；正式 OTA 按阶段扩大。
- GitHub Issues 是既有任务系统。本轮已进入本地实施；远程 Issue、PR、推送和发布以实际操作记录为准，不能由本计划或本地测试结果推定已完成。
- 改需求时更新产品目标、接口影响、成本/排期和受影响测试；进行中的小批次先保持可回退状态。安全与数据正确性修复不因需求变更被无声撤销。
- ECC 按需用于接口契约、架构评审和验证。它不代替实测，也不改变用户确认过的上下文与自动学习边界。

## 8. 首个开发周期及责任

先排一个 5 工作日目标周期；这是滚动计划，不是已承诺的完成日期。按“我负责软件整合与自动检查，用户负责实物准备、真实语音与体验确认，结构/电子/测试专业工作按需外协”估算。实物和可用人力变化后重新排期。

| 时间目标 | 软件线 | 实物线 | 可审查产物 |
| --- | --- | --- | --- |
| 第 1 天 | 对齐当前文档、版本与契约；固化截断和撤权回归 | 确认实际板型、接线、烧录版本与安全恢复包 | 基线清单、失败复现与验收表 |
| 第 2–3 天 | 关闭截断及共享撤权入口；网页与权益修复并行 | 录音链路诊断，已有 BOOT 路径测试 | 小提交、回归结果、输入诊断结论 |
| 第 4 天 | 关键修复稳定后，整合独立 Provider 绑定与豆包候选；验证音色、权限、取消、计量和路线往返 | 贯通一轮手动对话，补两条路线首音与 ACK 证据 | 单轮链路报告、替换测试结果 |
| 第 5 天 | 独立审查与集成复核；登记尚未关闭的问题 | 复测已定位问题，决定后续声学/硬件工作 | 本周期交付单、下一周期的工作量与依赖 |

进入 G3 后才能依据实测估计试用日期；进入 G5 后再估计小批零售日期。硬件返工、物料交期、实验室和市场审核单列，不藏在软件天数里。20 台试用至少观察 7 天，继续收集 30 日留存与返修数据，不把一周小样本当成长期可靠性证明。

## 9. 后续需求的插入方式

| 新需求 | 首先调整的边界 | 必须追加的验证 |
| --- | --- | --- |
| 换同协议模型 | 模型/端点/凭据配置和能力检查 | 质量、延迟、音色、成本与取消 |
| 新服务商协议 | 对应角色适配器和注册项 | 统一契约、主备、格式与真实服务测试 |
| 换引脚或同平台板型 | 板型配置和驱动实例化 | GPIO/启动约束、声学、构建与受影响整机测试 |
| 换新屏幕/麦克风 | 外设驱动、尺寸/音频与校准配置 | 显示资源、输入输出质量和长稳 |
| BLE 全程通信 | BLE 传输与手机/网关 | 分包、流控、断线、后台存活、认证与体验 |
| 自然语音插话 | 端侧采集/AEC/VAD与会话取消 | 回声、误打断、双向音频与资源压力 |
| 非 ESP 平台 | 平台驱动与音频库移植 | CPU/内存/实时性与所有受影响硬件功能 |
| 海外首发 | 区域部署、语言/时区、服务商、支付和运营 | 目标市场网络、真人语音、数据隔离及适用要求 |

海外默认采用独立区域环境、凭据、数据库与备份，国内记忆不自动迁移；这是一项待目标市场确定后验证的设计建议。现阶段不接入未选定市场的支付商、不混用货币计费，也不承诺某个算法或芯片永远适用。

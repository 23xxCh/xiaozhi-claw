# 阿里应用上传积压：复现与局部优化

## 证据与结论

此前四条完成记录首响 1.610/2.540/2.348/2.703 秒；其中三条输入收尾约 1.27–1.31 秒。服务端收到的音频时长比接收跨度长约 1.3 秒，说明存在成批到达的已采集音频；历史日志不足以把初始缓存全部归因于设备或建连。

使用同一段 3.78 秒音频、真实 FFmpeg 编解码、模拟供应商接收，重放“首批带 1.3 秒缓存，后续实时到达”：旧上传节奏使收尾等待 1.329 秒。无缓存的基线约 0.03 秒。因此已证实共享输入桥的实时限速会把已有积压一直保留至轮末，不是 FFmpeg 固定需要 1.3 秒收尾。

## 修改边界

阿里适配器使用 push2talk。官方要求 SendSpeech 后立即上传音频，以 StopSpeech 结束输入；不同于 tap2talk/duplex 的持续实时上传建议。参考：[阿里实时多模态交互协议](https://help.aliyun.com/zh/model-studio/multimodal-interaction-protocol)。

只在阿里托管应用工厂创建 SpeechToSpeechInput 时设置 pace_input=False。音频到达且解码就绪即可 await 发送，不再增加与音频时长相同的 sleep。保留 20ms PCM 块、既有有界队列、WebSocket 背压、鉴权/取消及完整输入后提交。其他路线保留原实时节奏，没有更换模型、改采样率或丢帧。

## 验证

同一回放的新收尾低于日志 1ms 分辨率；无初始缓存的新收尾约 0.016 秒。三组输出均为 60480 个样本，SHA256 相同：`9f700bdff4ea3f8b9d4a00fc145da0f5e7d93cafe1f08e2cb6b8837b869d97e3`。

新增检查逐块确认顺序与内容一致，确认最后一个样本发送后才提交；真实 FFmpeg 测试与独立整段解码参考逐字节一致。相关输入节奏、解码、S2S、阿里/豆包适配器及网关回归共 91 passed，Ruff 通过。首次测试的目录启用断言受本地 ALIYUN_DIALOG_ENABLED 影响；按测试默认关闭该环境开关后通过，没有改生产配置。

这不是云端性能验收：模拟接收方没有网络/ASR/LLM/TTS 延迟，不能据此宣布真实首响已降至一秒。下一次真机对话需观察 pace_input=False、upstream_input_ended、最终识别和 speaker_pcm_started，同时确认尾字、连续多轮及停止恢复。

初始约 1.3 秒缓存的精确形成位置仍待新证据定位；本次首先去掉已经证实的重复限速等待。部署只重启本地网关，不刷固件；长稳以更新后的新起点重新累计，不能合并两个版本的成绩。

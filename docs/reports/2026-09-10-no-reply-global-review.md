# 不回复故障：跨层代码审查

审查日期：2026-09-10。基线：本地 b8e78e1，feature/hensun-stability-quality。

## 结论与范围

主要缺陷集中在固件与网关共同控制轮次，却没有一致的输入结束、事件归属和超时契约。测试对源码形状的检查不能证明异步行为正确，反复局部修补因此容易留下相邻故障。没有证据表明更换 FastAPI、Next.js 或数据库能够解决本次问题。不建议全面重写或拆微服务。

本次沿固件采集、VAD、编码与发送、网关输入、阿里适配器、回复取消、错误展示、测试和本地运行方式进行了交叉检查；参考既有网页、数据库与部署检查记录。不是全部代码逐行安全审计，也不是七条路线新的真机验收。本次只增加审查记录，没有修改运行逻辑或烧录。

## 当前现场能证明什么

当前网关日志 run/local-pilot/gateway-20260910-090216.log.err 第 9–22 行记录一个失败轮次：17 个 Opus 包，声明音频时长 1020ms；向阿里发送的 PCM 共 32640 字节，随后发出 StopSpeech。没有最终识别文字，结果为 turn-cancelled，随后设备重新连接。

这证明至少这一轮音频上传到了网关并向供应商发送，不等于音频包含完整有效的人声。没有同期串口、录音和精确取消来源，不能断定本轮由麦克风、供应商或下面某个竞态单独造成；也不能把用户说的多句话虚报为多条已捕获失败样本。

## 优先问题

### P1：停止消息可能越过尚未发出的音频

- firmware/xiaozhi-esp32/main/application.cc:344：同一事件循环先处理 STOP_LISTENING，再处理 SEND_AUDIO。
- 同文件 :1480：停止处理直接 SendStopListening，然后进入 Idle，没有等待当前编码任务和发送队列收尾。
- firmware/xiaozhi-esp32/main/audio/engines/afe_audio_engine.cc:463：VAD 结束回调发生在当前 PCM 交给输出回调之前；编码又是异步执行。
- backend/realtime/session.py:2319：回复处理任务仍运行时，收到的后续二进制帧被忽略。

可达顺序为：VAD 结束 → 固件发送 stop → 网关开始处理 → 剩余编码帧才发送，被忽略或在固件清队列时丢弃。这个静态路径成立，但尚未对本轮做调度重放证明。交换两个事件处理分支不够，因为编码可能还未完成。

修复契约：停止采集、完成本轮编码与有界队列发送、最后只发送一次输入结束。取消另走立即失效路径。必须覆盖 stop 与最后一帧同时就绪，以及编码尚未结束两种情况。

### P1：跨层超时不同步，失败退回待机而原因丢失

- application.cc:29、460：等待回复保护为 12 个时钟 tick，触发 reply-timeout 并关闭对话。
- backend/realtime/aliyun_dialog.py:32、233：默认单次接收超时为 15 秒；事件持续到来会重新开始等待，不能等同于输入结束后的最终识别期限。
- backend/realtime/s2s.py:342：外层事件循环另有 120 秒期限。
- aliyun_dialog.py:272：Listening 状态仅设置事件；未收到最终文字时没有独立的输入后无结果期限。
- application.cc:1091：网关 error 只取 code 后退出对话，没有展示服务端 message 或按可恢复性处理。

设备可能先于上游错误处理退出，服务端最终只留下 turn-cancelled。以上时间分别作用于不同层，不能简单调大一个值就认为修复。

修复契约：分别定义连接、输入结束到结果、生成、播放期限；网关给出明确终态和用户提示，设备最后一道保护晚于正常错误反馈。可恢复失败完成旧任务清理后只自动再开一次聆听窗口，持续失败要求用户重试。

### P1：排队的 VAD 事件没有采集轮次归属

application.cc:127 的回调把 speaking 放入 Schedule 队列，但没有携带采集代次。执行时只判断当前是否 Listening/AutoStop。上一轮延迟事件若到达下一轮的 Listening，仍可能修改新一轮标志并停止收音。

AFE 内部已有 generation/reset 防护，但没有贯穿到应用回调。此前 reset_vad 补丁覆盖了处理器内部状态，没有证明排队事件不会跨轮。这是潜在竞态，尚未通过本轮日志证实触发。

修复契约：将现有采集代次贯穿到 VAD、停止请求和异步完成事件，只允许当前代次改变会话状态；避免再增加彼此独立的布尔补丁。

### P1：回归测试与用户故障的验证层次不匹配

firmware/xiaozhi-esp32/scripts/tests/test_hensun_nocam_pilot.py 中多项检查使用 assertIn/assertRegex 比较源码，包含此次之前的 capture reset 检查。这能防止代码片段消失，不能验证事件顺序、编码尾帧、旧轮次回调或真实音频。后端模拟测试也不能替代设备调度验证。

需要动态重放：延迟 VAD、stop/尾帧并发、无最终 ASR、供应商有事件但不完成、取消后迟到音频、旧任务清理与新轮开始竞争。七条路线复用同一组轮次不变量，真实口测单独保留失败样本与版本。

### P2：建立上游与接收音频串行，存在额外缓冲延迟

backend/realtime/session.py 的 open_asr_for_turn 在设备消息循环中等待上游建立；当前样本建连 359ms、首 PCM 313ms、输入结束后收尾 500ms。上传实时节奏控制还会限制积压音频追赶。不能将这些耗时简单相加，也不能凭它们声称供应商本身慢。

先记录同一轮完整时间轴，再判断是否复用供应商会话或提前建立连接。保留有界缓冲和真实首响口径，不能靠丢尾音换取延迟数字。

### P1 运维缺口：本地启动成功不等于持续可用

scripts/start_local_pilot.ps1 使用 Start-Process 启动服务，没有持续监督与自动恢复循环。既往本地进程退出原因仍未确定。云端 Compose 的 restart/healthcheck 与本地不同，不能据此声称云端已完成异常恢复验收。

日志应保存取消原始来源、采集代次、轮次、固件/服务版本和时间；目前泛化为 turn-cancelled 会掩盖设备超时、断线和主动停止之间的区别。部署验收需实际杀进程、重启和恢复记录。

## 为什么反复发生，以及接下来怎么做

之前的修复覆盖了具体复现点，却没有充分证明跨端生命周期整体成立；源码断言与一次成功口测被赋予了过高信心。这属于实现架构边界和验证质量问题，不能都归因于硬件或供应商。

1. 暂停新增路线行为和音频参数试错，保留现有七条入口；先固定失败样本及版本。
2. 优先修复输入结束屏障与采集代次，增加可执行的异步顺序回归；不全面改写项目。
3. 统一无结果、取消、超时及一次恢复窗口，再验证错误提示确实到达 TFT。
4. 在同一版本完成唤醒、BOOT、回复后追问、短句、无声、断线与迟到事件测试；随后逐路线口测与延迟统计。
5. 完成云端监督、恢复与版本证据后重新评分。现阶段不宣布本次故障已修复，也不提高商业交付评分。

网页和数据库目前没有证据是这次无回复的主因；仍须按周计划分别验收账号隔离、配置生效、迁移恢复与记忆删除，不以语音修复替代这些检查。

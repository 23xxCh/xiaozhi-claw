# 本地进程恢复与长稳观察

当前固件保持用户确认“可以正常聊天”的版本，本次没有改动语音、模型或固件。

## 已实施

`scripts/local_pilot_supervisor.py` 接管 processes.json 中的控制面、实时网关和网页进程。验证命令、工作目录及进程创建时间，避免 PID 重用导致误操作；端口已被占用时拒绝重复启动。Windows venv 的启动器和实际监听子进程分别记录。

进程退出后自动启动原服务，不修改环境、数据库或迁移，也不重新构建。每项服务十分钟最多三次尝试；启动失败退避后再尝试。健康状态变化及每分钟采样写入 supervisor-events.jsonl，当前状态原子写入 supervisor.json。Python 服务启用 faulthandler。接管前退出的进程无法追溯退出码，记录 null，不伪造原因。

start_local_pilot.ps1 自动确保守护进程运行，重复调用不创建第二个守护进程。stop_local_pilot.ps1 先请求守护进程退出，等它退出后重新读取服务 PID，再停止服务，防止正常关机触发自动拉起。

## 已验证

- 工具检查 36 passed，Ruff 通过；PowerShell 停止脚本语法解析通过。
- 实际终止控制服务后自动恢复，健康观测耗时 16.05 秒。
- 实际终止网关后自动恢复，健康观测耗时 14.05 秒；新网关日志确认设备 WebSocket accepted/connection open。
- 实际终止网页进程后自动恢复，健康观测耗时 11.06 秒。
- 重复 ensure 保持同一守护进程；三个服务当前健康。实际演练数据位于 run/reports/local-recovery-injection.json。

## 尚不能下的结论

没有找到之前控制服务退出的明确原因：原日志只有启动记录，查询的近期 Windows Application 1000/1001 事件未提供相关证据。此次解决的是可观察性和自动恢复，不能宣称历史崩溃根因已解决。

健康接口不健康只记录，不自动杀进程，因为依赖故障也会影响就绪检查。尚未实现卡死进程自动重启、Windows 开机启动或守护进程自身的系统级恢复；本工具不是 Windows Service。服务重启时正在进行的对话仍可能失败，需要用户重新唤醒。

## 八小时观察：进行中

在全部退出演练后记录最新 soak-start，之后每分钟采集服务健康。已安排八小时后的自动复查，检查样本连续性、异常退出/重启、接口健康及设备连接，生成通过或未通过结论后暂停复查。电脑或 Codex 不能运行时复查可能延后，空白期间不能算健康。

这项观察仅证明服务可用性。真人连续多轮、截尾、表情、延迟和七条路线验收仍须分别记录；目前没有八小时完成结果。保持电脑开机且不休眠，按日常方式聊天即可，故障注入不能混入正常长稳统计。

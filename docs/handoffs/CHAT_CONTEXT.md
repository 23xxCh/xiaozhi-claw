# Hensun Desk 聊天决策时间线

> 这不是逐字聊天存档，而是给后续 Agent 使用的去噪决策记录。它只保留已经影响产品、代码、硬件或验收的事实；探索性说法若被后续决定推翻，以最新决定为准。最后核对：2026-08-18。

## 1. 项目起点：先让现有 ESP32 能工作

用户最初使用 ESP32-S3 CAM、2 英寸 TFT、麦克风、扬声器和摄像头扩展板，先后处理了 CH340 驱动、USB 数据线、COM6、烧录与配网问题。硬件已证明可以：

- 通过 CH340/COM6 烧录。
- 屏幕正常显示多色表情。
- 麦克风和扬声器完成小智官网语音对话。
- 摄像头代码与远程拍照能力保留。

这段经历形成了两个长期边界：不要因为语音问题删除摄像头；普通迭代不得擦除 NVS、Wi-Fi 和设备身份。

## 2. 从“小智官网版”到“双固件”

项目先采用小智官网完成配网、智能体配置和语音闭环。官方协议本身会下发独立 `llm emotion` 事件，因此官网版不应依赖提示词正文中的 `[mood:...]` 标签，也不应解析或朗读这种标签。

随后决定保留两条固件路线：

- 官网版：作为已知可用的回退通道。
- 自有版：连接 Hensun Bootstrap/WSS，模型、用户、设备、OTA 和合规能力由自有系统管理。

两版必须使用独立固件名和 OTA 发布环，禁止互刷。

## 3. 商业与产品边界收敛

产品定位逐步收敛为 18+ 成人桌面 AI 助理与轻陪伴。当前阶段不包含支付、儿童模式、虚拟恋人、医疗/心理治疗宣传、电池、轮式底盘和充电座。

家庭模式曾做过架构规划，但在法律、安全和监护流程完成前保持关闭；对外仍按 18+ 表述。摄像头首版不做云端视觉上传。

## 4. 表情路线：从状态原型到原创横屏动画

早期先验证 12 状态、再扩展到 36/60 个语义事件。真机证明屏幕刷新、颜色和切换可以稳定，但单纯用程序图元绘制的表情不够精致。

之后参考乐鑫三段式动画思路，确立：

```text
Entrance 进入 → Loop 循环 → Return 回归
```

表情必须原创，黑底柔白，不能直接复制外部示例。经过竖屏验证后，用户要求把整机物理横放，最终建立 320×240 横屏资源和独立本地固件。横屏效果得到用户确认。

后续又加入睡眠、唤醒、聆听、思考、说话和情绪状态。当前需要区分：

- 系统/展示状态：当前资源包有 12 个。
- 后端对话标签：支持 10 类 `[[face:...]]`。
- 真机独立说话脸：当前只完整接入 `neutral/happy/caring` 三套。

不要再用“60 个语义事件”宣称“60 套独立全帧动画已经完成”。

## 5. 自有网关与控制台

用户决定完全迁移到自有系统，方便二次开发、客户配置、合规、工厂烧录和量产。架构选择为单仓库、控制面与实时网关分进程：

- FastAPI 控制面：账户、邮箱登录、设备、认领、助手、配置、OTA、用量、审计和后台。
- 独立实时网关：设备 WSS、音频流、ASR/LLM/TTS、打断、播放确认、工具和表情控制。
- Next.js 控制台：客户使用；内部后台使用独立权限入口。
- SQLite：当前本地金样机。
- MySQL 8：Staging/生产目标。

首版不引入 Redis 和微服务。用户不能看到 Provider 地址或 API Key，只能选择产品化预设。

登录路线已经从微信扫码改为邮箱验证码；文档或页面不得再把微信回调写成当前前提。

## 6. 模型链路与情绪归属

当前默认链路：

```text
Qwen 实时 ASR → DeepSeek 流式 LLM → Qwen 实时 TTS
```

Qwen ASR 的情绪描述的是“用户说话时的情绪”，不是机器人回答的表情。机器人表情由设备状态、安全规则、情绪路由和同一次 LLM 回复中的受控 `[[face:...]]` 标记共同决定，不另发一次 LLM 分类请求。

表情标记必须从 TTS、用户可见正文和日志中完全移除，每轮最多两次变化。

## 7. 语音问题的主要根因与修复方向

项目曾反复出现“说多次才回复、ASR 等十几秒、TTS 漏字/窜字/断音、表情先说话但没声音、上一轮串到下一轮”。已经确认的根因和约束包括：

- ESP32 上传的是裸 Opus 包，实时 ASR 需要正确的流式 Ogg-Opus 封装。
- 实时 ASR 失败时必须用同一轮内存音频做批量降级，不能无声卡住。
- TTS 不能突发发送；设备队列会溢出。网关要按 60ms 匀速下发并实施背压。
- 播放必须走 `start → ready → PCM → stop → drained`。
- `tts.start` 不是“已经出声”；第一块真正送入扬声器的 PCM 才能触发说话表情。
- `turn_id + reply_id` 用于隔离旧轮次消息。
- 回复结束必须以本地解码器和扬声器排空为准。

这些约束优先级高于继续增加模型、工具或表情数量。

## 8. 多轮对话、停止和软睡眠

用户要求自然多轮，不应每一轮都重新说唤醒词。当前目标状态链：

```text
sleep → wake → listening → recognizing → thinking
→ speaking → settling(约800ms) → echo guard → listening(10s) → sleep
```

- “你好小灿”负责本地唤醒。
- BOOT 待机时开始对话；活动时立即停止并软待机。
- “小灿闭嘴”是服务端退出意图。
- 软睡眠保留 Wi-Fi、本地唤醒和 BOOT，不进入深睡眠。

当前本地横屏金样机采用一次唤醒后的 10 秒自然续聊。ESP32-S3 CAM 为半双工，播放期间不开麦；播放排空后先经过余响保护，再真正启动麦克风和 10 秒计时。短于 900ms 的续聊脉冲以及仅含“嗯、啊、呃”等语气词的 ASR 结果不进入 LLM/TTS，避免幽灵轮次。10 秒无人讲话时只切换睡眠表情，不朗读休眠文案。

## 9. 嘴型与表情连贯性迭代

说话嘴型经历过白色圆环、椭圆和“香肠嘴”等失败方案。用户最终接受的是细线 U 形五档嘴型：

- 嘴型作为 PCM 叠加层，不为每种情绪生成五套完整 GIF。
- 20 FPS，每 50ms 最多移动一档。
- 连续静音超过 300ms 闭嘴。
- 一轮中情绪更新不重新播放整张脸的入场动画。
- 显示切换使用容量为 1 的 mailbox 和 generation，旧请求不排队插入。

资源索引还发现过文件名槽问题：`talk_neutral.eaf` 正好占满 16 字节，没有结尾 `NUL`，运行时被判无文件。内部名称已改为 `talk_base.eaf`，并加入回归测试。

## 10. 本地、公网与当前优先级

项目曾把 Staging 部署到 `staging.hensun-desk.top` 并做公网真机验证，但公网链路放大了延迟、无声轮和状态不同步问题。用户随后明确要求先回到本机把核心功能做好。

当前活动主线固定为：

1. 本地三进程稳定运行。
2. 当前一台 ESP32 成为可恢复金样机。
3. 完成 30 轮、2 小时运行和 8 小时待机验收。
4. 审查并拆分当前脏工作树提交。
5. 通过后再恢复 Staging 和扩展其余七类独立说话脸。

在此之前暂停搜索、MCP 扩展、声纹、支付、小程序、新硬件和继续堆表情数量。

## 11. 用户的验收语言应如何理解

用户在真机迭代中会直接反馈“没反应”“卡住”“断音”“可以了”。其中：

- “可以了”表示当前肉眼/耳朵体验通过该轮人工检查，不等于自动测试、30 轮或长稳已经通过。
- 只有串口日志、ACK、哈希、测试结果和平台可见状态能证明对应技术步骤完成。
- 不得因为屏幕亮了就宣称 WSS/模型正常，也不得因为 HTTP 返回就宣称配置已应用。
